10 / normalization

Normalization: ทำไมไม่รวมทุกอย่างไว้ตารางเดียว?

ตารางเดียวที่รวมทุกอย่าง

OrderID | CustomerName | Product1 | Product2 | ProductPrice

  • ข้อมูลลูกค้าซ้ำหลายแถว

  • เพิ่มสินค้าใหม่โดยยังไม่มี Order ทำได้ยาก

เป้าหมายของ Normalization

15 / joins

JOIN: รวมข้อมูลหลายตารางอย่างมีความหมาย

ชนิดผลลัพธ์โจทย์ที่ใช้จริง
INNER JOINเอาเฉพาะแถวที่จับคู่กันได้รายชื่อลูกค้าที่มี Order
LEFT JOINเก็บทุกแถวฝั่งซ้าย เติม NULL เมื่อไม่พบคู่หาลูกค้าที่ไม่เคยสั่งซื้อ
RIGHT JOINเก็บทุกแถวฝั่งขวาเทียบได้ด้วยการสลับตารางเป็น LEFT JOIN
SELF JOINตารางเดียวกันทำหน้าที่ 2 บทบาทผู้แนะนำกับผู้ถูกแนะนำ
SELECT u.fname, o.order_date
FROM users u LEFT JOIN orders o
ON u.id = o.user_id
WHERE o.id IS NULL;
เทคนิคโจทย์: LEFT JOIN + right_table.key IS NULL = หาแถวที่ “ไม่มีคู่”
แยก ON = เงื่อนไขจับคู่ กับ WHERE = เงื่อนไขกรอง15 / 19
16 / advanced query

Subquery และ View: Query ซ้อน Query และผลลัพธ์ที่บันทึกชื่อไว้

Subquery

คำสั่ง SELECT ด้านในทำงานก่อน แล้วส่งผลให้ Query ด้านนอก

SELECT name, price
FROM products
WHERE price > (
SELECT AVG(price) FROM products
);

ใช้กับ IN เมื่อได้หลายค่า และ EXISTS เมื่อต้องการเช็กว่ามีแถวหรือไม่

View

บันทึก Query ที่ใช้บ่อยเป็นชื่อเสมือนตาราง

CREATE VIEW user_spending AS
SELECT user_id, SUM(amount) total
FROM orders
GROUP BY user_id;

ช่วยซ่อนความซับซ้อนและควบคุมสิทธิ์ แต่ View ที่มี Aggregate มัก Update ย้อนกลับไม่ได้

17 / normalization in practice

Normalization ให้ลึกขึ้น: Dependency และ Denormalization

Anomaly ที่ต้องกำจัด

  • Insert: เพิ่ม Department ไม่ได้ถ้ายังไม่มี Employee
  • Update: แก้เงินเดือนต้องแก้หลายแถว เสี่ยงไม่ครบ
  • Delete: ลบ Employee แล้วข้อมูล Department หาย
Functional Dependency: ถ้า A กำหนดค่า B ได้ เขียน A → B เช่น employee_id → employee_name

Denormalization

“ตั้งใจ” เพิ่มข้อมูลซ้ำหลัง Normalize แล้ว เพื่อให้การอ่านเร็วขึ้น

  • เหมาะกับ Dashboard/รายงานที่อ่านบ่อย
  • ลด JOIN และภาระ Query
  • แลกกับพื้นที่และความเสี่ยงข้อมูลไม่ตรงกัน

หลักจำ: Normalize first, denormalize deliberately.

ไม่ใช่การย้อนกลับแบบไร้เหตุผล ต้องวัด Performance และคุมการ Sync17 / 19
18 / safe SQL

SQL ที่ถูกต้องต้องปลอดภัยด้วย

อันตราย: ต่อ String จาก Input

SELECT * FROM users
WHERE email = '' + userInput + '';

ผู้ไม่หวังดีอาจใส่เงื่อนไขแปลกปลอม เช่น ' OR '1'='1 จนข้ามการตรวจสอบ

ทางแก้: Parameterized Query

SELECT * FROM users
WHERE email = $1;
params: [userInput]

แยกโครงสร้าง SQL ออกจากค่าที่ผู้ใช้กรอก DBMS จึงมอง Input เป็น “ข้อมูล” ไม่ใช่คำสั่ง

Write-query checklist: ทดลอง SELECT ด้วย WHERE เดียวกันก่อน, ตรวจจำนวนแถว, ใช้ Transaction เมื่อแก้หลายตาราง, และห้ามฝัง Input ลง SQL โดยตรง
จาก Assignment: SELECT ผิดเห็นข้อมูลผิด แต่ UPDATE/DELETE ผิดอาจทำลายข้อมูล18 / 19
19 / SQL deep dive

โครงสร้าง SELECT: อ่านจากโจทย์เป็น Query

SELECT category, AVG(price) AS avg_price
FROM products
WHERE stock > 0
GROUP BY category
HAVING AVG(price) > 500
ORDER BY avg_price DESC
LIMIT 3;

แปลโจทย์ทีละคำ

  • “ราคาเฉลี่ยแยกตามหมวด” → GROUP BY category
  • “เฉพาะสินค้าที่มีของ” → WHERE stock > 0
  • “เฉพาะหมวดที่เฉลี่ยเกิน 500” → HAVING
  • “แพงที่สุด 3 อันดับ” → ORDER BY ... DESC LIMIT 3
เหตุผล: WHERE ทำงานก่อนรวมกลุ่ม ส่วน HAVING ทำงานหลัง Aggregate จึงใช้แทนกันไม่ได้
ตัวอย่างจาก Assignment: COUNT, SUM, AVG, GROUP BY, HAVING, ORDER BY, LIMIT19 / 28

33 / higher normal forms

Normal Form ที่สูงกว่า 3NF: BCNF, 4NF, 5NF

BCNF

ทุกตัวกำหนดต้องเป็น Candidate Key

เข้มกว่า 3NF แก้กรณีที่ Non-key หรือ Candidate บางตัวทำให้เกิด Dependency ผิดรูป

4NF

จัดการ Multivalued Dependency

ถ้า Employee มี Skill หลายอย่างและ Language หลายภาษาอย่างอิสระ อย่าจับคู่ทุก Skill กับทุก Language ในแถวเดียว

5NF

จัดการ Join Dependency

แยกความสัมพันธ์ที่ประกอบจากหลาย Join จนการรวมกลับไม่สร้างคู่ปลอม

ใช้เมื่อไหร่: งานทั่วไปมักหยุดที่ 3NF/BCNF; 4NF/5NF ใช้เมื่อมีความสัมพันธ์หลายค่าหรือกฎธุรกิจซับซ้อนมาก

CTE: WITH

ตั้งชื่อผลลัพธ์ชั่วคราวให้ Query ยาวอ่านเป็นขั้นตอน

WITH high_earners AS (

Recursive CTE ใช้เดินโครงสร้าง เช่น แผนผังหัวหน้างาน

View: ชื่อถาวรของ Query

  • ช่วย Reuse และควบคุมสิทธิ์
  • View ธรรมดาอาจ Update ได้
  • View ที่มี GROUP BY/Aggregate มัก Update ไม่ได้โดยตรง
แยกให้ออก: CTE อยู่เฉพาะคำสั่งหนึ่ง; View อยู่ใน Schema จนกว่าจะ DROP

38 / complete join toolkit

JOIN ที่เหลือ: CROSS, FULL OUTER และ USING

CROSS

Cartesian Product

จับทุกแถวของ A กับทุกแถวของ B: A มี 3, B มี 4 ได้ 12 แถว

ใช้สร้างชุด Combination แต่ระวังผลลัพธ์พุ่ง

FULL

ทุกคนจากทั้งสองฝั่ง

รวมผลของ LEFT และ RIGHT; แถวที่ไม่มีคู่จะมี NULL

ใช้ตรวจความแตกต่าง/กระทบยอดสองระบบ

USING

คอลัมน์ชื่อเดียวกัน

ย่อ ON a.id = b.id เป็น USING (id) และแสดงคอลัมน์ร่วมครั้งเดียว

ใช้เมื่อชื่อและความหมายของคอลัมน์ตรงกันจริง

SELECT *
FROM department d
FULL OUTER JOIN project p
ON d.id = p.dept_id;
เลือกรูปแบบจากคำถาม: ต้องเก็บฝั่งไหนครบ? ต้องการเฉพาะคู่? หรืออยากเห็นข้อมูลที่ไม่ match เพื่อหาความผิดปกติ?
JOIN ต่อคอลัมน์; UNION ต่อแถว; CROSS JOIN ไม่มีเงื่อนไขจับคู่38 / 40
39 / rewrite and scale

ปรับ Query ให้เร็วขึ้นก่อนเพิ่มเครื่อง

Query Rewriting

  • เลือกคอลัมน์ที่ใช้จริง แทน SELECT *
  • กรองให้เร็วและกรองก่อน JOIN เมื่อทำได้
  • หลีกเลี่ยง Function ครอบคอลัมน์ที่มี Index เช่น YEAR(date)
  • ใช้ EXISTS เมื่ออยากเช็กการมีอยู่ ไม่ต้องดึงข้อมูลทั้งหมด
  • ให้ Optimizer ทำงาน แล้วตรวจด้วย EXPLAIN ANALYZE
-- เสี่ยงใช้ Index ไม่ได้
WHERE YEAR(created_at) = 2026

-- มักเหมาะกับช่วงวันที่
WHERE created_at >= '2026-01-01'
AND created_at < '2027-01-01'

เมื่อ Index ยังไม่พอ

  1. Partition แบ่งตารางตามช่วงวันที่/ภูมิภาค
  2. Read Replica แยกภาระอ่านจาก Primary
  3. Cache เก็บผลลัพธ์ที่อ่านซ้ำ
  4. Materialized View เก็บผลรวมที่คำนวณไว้
  5. Sharding กระจายข้อมูลเมื่อระบบใหญ่มาก
ลำดับคิด: เขียน Query ให้ถูก → วัด Plan → Index/Rewrite → ค่อย Scale
ประสิทธิภาพคือการแลกเปลี่ยนระหว่างเวลา พื้นที่ ความสดของข้อมูล และความซับซ้อน39 / 40
40 / schema and objects

Schema, Instance และวัตถุในฐานข้อมูล

Schema vs Instance

  • Schema = แบบแปลน/คำอธิบายโครงสร้าง เช่น ตาราง คอลัมน์ Key Constraint
  • Instance = ข้อมูลจริง ณ เวลาหนึ่ง
  • เพิ่มข้อมูลมักเปลี่ยน Instance; เปลี่ยนคอลัมน์คือเปลี่ยน Schema
เปรียบเทียบ: Schema คือแบบบ้าน; Instance คือเฟอร์นิเจอร์ที่อยู่ในบ้านวันนี้

Database Objects

  • Table เก็บข้อมูลถาวร
  • Index ช่วยค้นเร็ว
  • View ตารางเสมือนจาก Query
  • Procedure/Function รวม Logic เรียกใช้ซ้ำ
  • Trigger ทำงานอัตโนมัติเมื่อ INSERT/UPDATE/DELETE
ALTER TABLE employee ADD COLUMN phone VARCHAR(20);
CREATE VIEW active_users AS SELECT * FROM users WHERE status = 'active';
DDL เปลี่ยนแบบแปลน; Object แต่ละชนิดช่วยแก้ปัญหาคนละแบบ40 / 42

SELECT s.name, c.title, e.grade
